- Status: **approval-neutral candidate-byte baseline; authoritative release
  status is external and digest-bound**
- Audience: maintainers, reviewers and the project owner
- Research cut-off: **29 July 2026**

Outcome for the frozen candidate: external G9 evidence records `approved` for

`6a29e38e7bb805aafb7f36ba8d1fa4ce976875f45997049cd4808d6ede7f75e1`.

This is the dependency-ordered operating record for the v0.3.0 candidate. It
is not a review receipt, approval or release record. Candidate bytes preserve
a `not_run` baseline and do not self-assert their current gate state. Only
version-scoped evidence bound to the final candidate identity records a gate
result, owner decision or release and deployment authority.

The final v0.2.0 receipts and release metadata are historical. They remain
useful regression evidence, but cannot approve changed v0.3.0 bytes.
The owner selected v0.3.0 dated 11 August 2026 for `CITATION.cff` and the
changelog before the candidate freeze. Both are governed inputs and therefore
cannot be changed after that freeze. They identify the intended version but do
not confer approval: the exact current G1–G9 state and release authority are
recorded only in subsequent version-scoped, digest-bound evidence. A later
input edit would be a new governed candidate, not a byte-identical promotion.

## Dependency-ordered runbook

Run these steps only after reviewing the complete authored diff. The build is
offline; local G1–G8 checks and browser journeys do not require a GitHub token.
Every Bash block is fail-fast. Run a complete block in one Bash process; do not
copy only the mutating command at its end. `OKF_REMOTE` is deliberately required
instead of defaulted: the transition checker requires exactly one credential-free
fetch destination and one credential-free push destination, both bound to
`github.com/chris-page-gov/okf-LandRegistry`, without printing either URL.

The governed build and metadata producer require exactly CPython 3.12.11 in
`.venv`, isolated mode, disabled bytecode writes and a fresh, external, empty
`0700` cache namespace. Create the environment with `--without-pip`, then use
an external installer with `--no-compile --require-hashes`; pip, `.pth` files,
startup customisers, bytecode and files outside the locked distribution
inventories are prohibited in the target. Every `runtime_cache` below must be a
new absolute directory and must not be reused for another command.

The first `git add` is the causal freeze: it stages every authored input while
leaving the generated bundle and later evidence surfaces untouched. The builder
then consumes and rechecks that exact stage-zero index. Only after the build is
the generated bundle staged and the complete staged candidate validated. A
failure before that validation is not a candidate and must not be committed.

The builder constructs the candidate at the exact, initially absent
`previous_output` path outside the repository. Its parent is a sibling of the
checkout, which keeps the swap slot on the same file system without adding an
untracked path to the candidate. One atomic directory exchange makes the new
candidate live and leaves the complete pre-build bundle at that exact recovery
path. The builder never deletes, prunes or overwrites it. Record the path with
the build log; moving or deleting it is a separate owner-authorised operation.
If the build or final input check fails, the live bundle remains intact and the
swap slot is retained for diagnosis.

The in-process observer starts after Python startup and initial imports; it
verifies the runtime before release work continues but does not attest the
exact source bytes already executed. The executable pre-invocation check
rejects `.pth`, bytecode and customiser hooks and holds a cooperating
single-writer lock for the build. This is a fail-closed operational mitigation,
not cryptographic proof against an uncooperative concurrent mutator. A pre-site
staged launcher would be needed to close that remaining gap and is proposed for
a future contract revision.

Run the deterministic calibration diagnostic. It is a regression result, not
independent G5 acceptance:


### 3. Freeze and reconcile the candidate

The complete candidate is already staged by step 2 while all diagnostic,
review and archive material remains outside it. The staged-candidate check compares the index
with the governed inventory in the staged build receipt, requires every input
to be a regular stage-zero Git blob with the exact byte count and digest,
rejects conflicts and partial staging, and refuses staged `validation/**` or
`dist/**` paths:

```bash
set -euo pipefail
OKF_REMOTE="${OKF_REMOTE:?set the verified canonical GitHub remote name}"
OKF_CANDIDATE_BRANCH="candidate/v0.3.0"
.venv/bin/python -B scripts/check_release_transition.py \
  remote-binding --remote "$OKF_REMOTE"
.venv/bin/python -B scripts/check_release_transition.py staged-candidate
.venv/bin/python -B scripts/check_release_evidence.py --staged-candidate

git commit -m "Migrate Land Registry to OKF v0.3 semantic candidate"
CANDIDATE_SHA="$(git rev-parse HEAD)"
.venv/bin/python -B scripts/check_release_evidence.py \
  --candidate-only \
  --candidate-commit-sha "$CANDIDATE_SHA"
```

Do not stage `validation/candidate-v0.3.0/evidence/evaluation-diagnostic.json`
in this commit. It belongs in a later evidence-only descendant. After the
intended candidate is committed, record its full 40-character Git SHA and the
complete release root from `bundle/CHECKSUMS.sha256` in the candidate-bound
validation evidence. Do not write the commit SHA back into a file governed by
that commit: doing so would create an impossible self-reference and a
different commit. Use a second, separate clean checkout for the reproducibility
build. Its generated bundle must remain byte-identical to the committed build

Never reuse the first build's swap slot. After the first build it contains the
pre-build bundle; after the clean-checkout second build the distinct second
slot contains the committed build 1 candidate and that checkout's live
`bundle/` contains build 2. Concrete recovery paths are operational results
only: the deterministic build receipt contains the stable placeholder
`<owner-selected-empty-same-filesystem-path>`, so different paths cannot change
the governed bundle bytes.

Any unexpected file—including a Git-ignored file—missing file, non-regular
path, digest mismatch or candidate identity change stops the run. Run build 2
only in the clean detached checkout and compare every governed byte before
recording G7 evidence. Retain that checkout and both recovery paths through
release verification; removing them is a later cleanup action.

The transition check binds each file's device, inode, type, size and change
times before and after reading, then repeats the complete ignored-inclusive
inventory. The following Pages upload is a separate action and therefore
depends on the GitHub-hosted job remaining a sequential, single-writer
workspace with no untrusted background mutator between those adjacent steps.
That trust boundary is residual deployment risk, not permission to run other
processes concurrently with release publication.

Every later commit may add only files below
`validation/candidate-v0.3.0/` or the two exact archives
`dist/okf-landregistry-0.3.0-candidate-a.zip` and
`dist/okf-landregistry-0.3.0-candidate-b.zip`. The NUL-safe staged-evidence
check below enforces that surface, batch-checks Git blob sizes, applies per-file
and aggregate ceilings, and rejects non-printable, non-NFC, hidden, temporary,
modified, deleted, renamed, conflicted, symbolic-link and non-stage-zero paths.
After each such
commit, rerun `--candidate-only` against `$CANDIDATE_SHA`. Never squash,
rebase or amend the candidate after evidence is bound: those operations lose
its identity. Do not merge a branch based before the candidate, because its
additional parent introduces the candidate tree after that parent and the
history check correctly fails closed.

no-replace directory rename. It
preserves byte-identical existing files, including their inode and modification

published as a one-file intermediate. A racing writer is accepted only when it
has already published the exact complete byte-identical directory. Cleanup
failure can leave only a hidden `.release-metadata-*` stage, which candidate and
evidence inventory checks reject. The command also revalidates the held parent
chain and fails closed on platforms without the required no-follow,
directory-descriptor and atomic no-replace rename semantics.
